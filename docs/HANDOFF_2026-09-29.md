Everything a new owner needs to pick this project up: where it stands, what changed in the last releases, how to
build, release and test it, and what is still open. Written after the 1.1.4 -> 1.3.5 run (2026-09-28/29); final update 2026-09-29 ~09:00 with the scale / frame-cap
flash results and the zoom-out verdict.

## 3. Architecture in one screen

- `fable2recomp` is a static recompilation of the Xbox 360 game (ReXGlue SDK, `RexBlue/win-amd64`; the SDK sources in
  `rexglue-src/` are **local only - never push them**).
- Rendering: `src/native_gpu_*` + `src/native_gpu_xlat/` (a vendored, patched copy of the SDK's D3D12 backend:
  `rtc_d3d12/command_processor.cpp`, `texture_cache*.cpp`, `render_target_cache.cpp`, `shared_memory*.cpp`). The game's
  PM4 command stream is decoded on a recorder thread and drawn on a draw thread (`ngpu_opt_split`); submissions go
  through an async submit thread (`ngpu_backend_async_submit`).
- Settings: `src/fable2_settings.h` (file `fable2_settings.cfg` beside the exe), applied to cvars by
  `src/fable2_tuning.h`; F10 menu in `src/fable2_menu.cpp`. Many GPU cvars are read ONCE at start (the menu marks them
  red).
- Texture pack: `textures/pack/<id16>-<crc32>.tex`, served by content hash + shape (`id & 0xFFFFFFFFFF`);
  `textures/dump/` for dumps; `tools/upscale_textures.py` builds the pack (F10 Process button).

## 4. Build and release

```
tools\build.cmd                                  # build (from fable2recomp, PowerShell or cmd)
python tools\native_gpu\p2_inject_exits.py --check --root <fable2recomp>   # must say 0 of 304 (no census exits)
python tools\make_release.py --build             # stage ..\Releases\v<VERSION> + zip; refuses stale builds
```
Then: commit, `git tag -a vX`, `git push origin tu1:main`, `git push origin vX`,
`gh release create vX <zip> --notes-file <notes>`, read the asset back (`gh release view --json assets`) and compare
its sha256 with the local zip. Gates used for every release: a **zip leg** (the exe extracted from the zip runs a
Fairfax stand, 0 failed draws) and, for renderer changes, a behavioural leg on that same exe.
- `VERSION` + a CHANGELOG entry are required; `make_release.py` renders README.txt's and the notes' Known issues
  from ONE list (`KNOWN_ISSUES`) - put new issues there.
- An existing `Releases\v<ver>` folder blocks a re-cut: move it to `Releases\_superseded\` (never delete).

uses its own folder). They assume the author's scratch area `D:\fable2_flash\ab110` (test arm, logs, captures) and

- **Verify every arm by a line the feature itself emits**, not by the config or the override: e.g. "internal scale
  NxN" + "resolution_scale = N" for scale, the `[swap]` guest fps (30.0, zero spread) for a frame cap, the ABSENCE of
  the async submit thread's own line for async-off.

  Lake, **stationary** camera pan, 190 s recording. Walking routes diverge between arms at different frame rates.
- Detectors: `pinkflip.py` (one-frame per-pixel flips with a blue-over-green shift; the one that sees the tree flash;
  false-positives on fast camera motion), `flashcount.py` (whole-frame neighbour test), `devcount.py`, `tilecount.py`.
  Sort frames numerically - past 10,000 frames `f10000.jpg` sorts after `f1000.jpg`.
- `burst.ps1` records the screen: whatever is on top. Check the foreground process (`shot.ps1` writes `.fg.txt`).

## 6. The tree-canopy flash - findings so far

Symptom: whole canopies turn violet/blue (sometimes white/cyan) for a frame, repeatedly; looks like a normal map drawn
as colour. User captures: `error.mp4` (frames 490/493/500) and `Error.png` in the repo root folder.

Measured (uwpan.sh, strong pinkflip frames per ~3 min; each "leg" one run):
- **Armed per session**: a run is dirty from start to end or clean from start to end. About 1 in 6 default runs reads
  0. So one clean run proves nothing; one dirty run refutes. Use >= 3 runs per arm.
- Default (`readback_resolve` = some): 482 / 516 / 595 (+ others) at ~49 fps.
- **Waiting cures it**: `readback_resolve_wait_only_kb` = 1 / 64 / 256 / 1024 / 4096 -> 0 / 6 / 0 / 1 / 1 at 21 / 25 /
  29 / 34 / 36 fps (5 of 5 clean). 8192 and 16384: 2 clean of 4 at ~48 fps. `readback_resolve = full`: 3 at 24 fps.
- **Refuted** (flashed): texture pack off; decode/draw split off; sampler memo; ROV render path; small-resolve
  submission boundary (64 KB); **boundary after every resolve** (SB_1, sustained runs up to 70 frames);
  on-demand readback (the CPU never touches the pages); readback none (0 then 10); async submit off (AS_1: 423);
  texture skip-unchanged / hoisted uploads off (worse, route-confounded).
- A candidate fix that kept older copy-backs from overwriting newer resolves made it **worse** (982/830/991): it
  effectively dropped almost all copy-backs (landings 20k -> 123 per 5 s). Kept as
  `docs/native_gpu/readback_order_REFUTED_2026-09-29.patch` - do not apply.
- **Twenty-second rule** (auditor, 19 legs, zero overlap): every dirty leg shows hot frames (violet share > 0.20%) in
  the FIRST TENTH of its capture (24-172 frames over 10 dirty legs), every clean leg (10) shows none. Stop a leg at the first hot frame and move
  on; a clean first tenth still needs the full leg, x3, before an arm counts as clean.
- Current reading: an **ordering** fault - something is used before the GPU has finished the rendered image it depends
  on; waiting before the recorder moves on removes it, a submission boundary alone does not. The busiest flashing
  shader binds the game's impostor atlases (format 6) in slots that usually hold DXT1 colour and DXN normal maps.
- Diagnostics patch (in-engine counters, slot-format detector): `docs/native_gpu/flash_instrumentation_2026-09-29.patch`.
- Next leads: find the CPU-side resource reused while the GPU may still read it (upload/constant buffer pages,
  descriptors) - waiting helps, boundaries do not; bisect with a wait placed after specific resolve classes only.
- **Scale and headroom tests (2026-09-29 morning, uwpan.sh stationary Bower Lake; each arm verified by the log's
  "internal scale NxN" and "resolution_scale = N" lines):**

  | Leg | Internal scale | Frame cap | Guest fps | Strong pinkflip frames |
  |---|---|---|---|---|
  | default (many legs) | 3x | 60 | ~49 (GPU-bound) | hundreds; peak 2.52% of pixels |
  | S1_1 / S1_3 | 1x | 60 | 60.0 | 0 / 1 (the 1 is texture noise, 9x below the weakest real flash) |
  | S1_2 | 1x | 60 | - | VOID (menu took no input, wrong save) |
  | S2_1 / S2_2 | 2x | 60 | 60.0 | 0 / 2 (noise) |
  | **FC30_1** | **3x** | **30** (`fps=30` in the cfg) | **30.0** (`[swap]` p50 33.3 ms), GPU 55% | **0** |

  Reading: every clean arm has spare GPU time; the only dirty setting is the one where the card cannot keep up
  (3x at 60). 2x still uses a scaled buffer and is clean, so "any scaled buffer" / the 1x-address copy mismatch
  (question 2 below) is no longer a live explanation on its own. FC30_1 keeps the 3x buffer and resolve unchanged
  and is clean - it supports **headroom / ordering** (the GPU running behind while something is reused or read)
  over "something specific to 3x". It is ONE leg and ~1 in 4-6 sessions reads clean at a broken setting, so repeat
  FC30 x2 before treating it as settled.
- **User-facing workaround today:** lower F10 Internal resolution to 2x (2560x1440) or cap the frame rate at 30 -
  both measured clean. Not yet written into the release notes / KNOWN_ISSUES (needs the repeat runs first).
- **Next step for a real fix:** the fault appears when the GPU is behind the CPU. Look for a resource the recorder
  reuses or overwrites while an in-flight submission can still read it (upload / constant pools, descriptor heaps,
  readback ring slots reused for a different key, shared-memory uploads over a just-resolved range). A good
  discriminator: at 3x/60, add a fence wait before ONE such reuse class at a time and apply the twenty-second rule.
  Artificial GPU load at 2x (e.g. a heavier post effect) that drops it below 60 should make it flash if headroom is
  the trigger.
- Open questions for the next session (from the auditor's reasoning, checked against the code):
  1. A copy-back is recorded as a GPU copy right after its resolve (`D3DCopyBufferRegion` into a private readback
     buffer, `command_processor.cpp` ~4470), and lands only after its own submission's fence - so "the copy reads the
     live target after the GPU re-rendered it" cannot happen in the simple form. Still check: can a readback ring slot
     be reused while its copy is pending for a DIFFERENT key (the ring guard covers the same key only)?
  2. That copy's SOURCE is the shared-memory buffer at the 1x address; at 3x the resolve writes the scaled buffer.
     Confirm the 1x bytes for the resolved range are written before the copy runs (the downscale path), or the copy
     reads stale 1x memory.
  3. Waiting (the recorder does not continue until the GPU is idle) cures it; a submission boundary does not. List what
     the recorder does between a resolve and the next frame that touches GPU-visible memory (upload/constant pools,
     descriptor reuse, shared-memory uploads of the resolved range) and test those one at a time with the 20-second rule.
- `Black texture fix` = Full removes it at ~half the frame rate; the scale/cap results above are cheaper workarounds.

## 7. Other open items

1. **Depth-of-field bleed at 3x and above** (known issue): distance blur spreads further around far edges against the
   sky. Cause not known (earlier "ruled out" causes were void test arms).
2. **Ultrawide pause/Up menu** is shown full width (circular map reads as an oval); menu fade drawn in a 16:9 band.
3. **Texture-pack prebuild budget** is 1.5 GB (15% of VRAM, `texture_cache.cpp PrebuildBudgetBytes`): Bowerstone Market
   (2.6 GB) and Slums leave 114-234 replacements out. A larger budget once caused a 550-600 ms readback wait; re-test
   with an A/B before raising it.
4. **Draw distance** scales only four fields in `globals.gdb` (max draw, override, billboard, LOD fade); much pop-in
   (grass, NPCs, shadows, region streaming) is outside it.
5. At 4K the draw thread is ~98% busy and the renderer waits ~2 s per 5 s on resolve readbacks; per-frame CPU cost is
   flat across resolutions.
6. **Step 2** (taking the game's Direct3D calls instead of the command buffer) is **halted** by the user.
7. **"Zoom out from the character when an area loads"** (user report, 09-29): NOT OURS - leave as is (user decision).
   Proved with a one-variable control: fast travel Fairfax -> Bower Lake with ultrawide on (ZM2) and off (ZM3), same
   exe; both show the hero close-up after the reveal and the camera easing back over ~1.3 s. With ultrawide off at
   fov 60 the FOV patch does not run at all. It is the game's own arrival camera. Save-load reveal (ZM1) showed none.
8. The in-game updater of an old install leaves `rexgpu-xenos.dll` behind (harmless).
9. **native-gpu lags tu1**: the 1.3.2 texture fixes were cherry-picked there (`83c903a`, `62e92b5`) but the 1.3.3-1.3.5
   menu/tool work (`f779f03`, `98b62be`, `66f30d9`, `ee58d3b`, ...) exists only on tu1. Bring it level before
   developing further on native-gpu.

## 8. Standing user decisions

- One game at a time; the user's play wins the machine. Close only processes you started (by PID).
- `readback_resolve` (Black texture fix) may change only if the hero/dog black-texture bug is verified fixed.
- A setting shown to break the game leaves every settings screen; restart-bound settings are marked red.
- Release after every change (bump, build, tag, publish), with the zip leg; never publish unverified claims - the
  1.3.4 None advice had to be withdrawn in 1.3.5.
- Back up before overwriting user installs; never touch the user's saves (the content root is the save folder).
